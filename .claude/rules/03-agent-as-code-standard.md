# The "Agent as Code" Standard

Every single sub-agent and orchestrator generated in this workspace MUST strictly adhere to the following physical and structural standards. These are Claude Code's real, documented conventions (last verified against Claude Code v2.1.296, its changelog and the official docs on 2026-10-12) — deviation produces a swarm that Claude Code silently fails to load. This applies to ALL generated swarms.

> **CANONICAL SOURCE:** This file is the single source of truth for the Claude Code file/frontmatter schema and the Model Routing Doctrine. Other files (CLAUDE.md, agent bodies) MUST reference this rule instead of restating its lists — duplicated copies drift out of sync and produce contradictions.

## 1. Physical Directory Structure
- **Orchestrator (`CLAUDE.md`):** MUST be written directly to the project root directory (e.g., `<project-root>/CLAUDE.md`). Plain markdown — Claude Code loads it automatically as project memory (since v2.1.277 a project with NO `CLAUDE.md` falls back to `AGENTS.md`; generated swarms always ship `CLAUDE.md`, never rely on the fallback). It may import auxiliary files with the `@path/to/file` syntax (expanded at launch, up to 4 hops) to stay modular.
- **Sub-Agents:** MUST be written to `.claude/agents/<agent-name>.md` — one file per agent. Never write agent folders to the project root, and never use the `.claude/skills/<name>/SKILL.md` layout for worker personas (skills are instruction packs, not isolated agents).
- **Global Rules:** MUST be written to `.claude/rules/<rule-name>.md`. Claude Code auto-loads every markdown file in this directory at startup. Scope a rule to file patterns with `paths:` frontmatter (glob patterns, brace expansion supported) when it only applies to part of the tree — path-scoped rules load only when Claude reads, writes or edits a matching file (Write and Edit trigger them since 2.1.288), keeping sessions lean.
- **Skills (optional):** Reusable multi-step procedures or domain playbooks MAY be packaged under `.claude/skills/` and preloaded into a specific agent via its `skills:` frontmatter. Skills are for on-demand procedural knowledge; always-mandatory standards belong in `.claude/rules/` (auto-loaded), never in skills.
- **Workflows (optional):** A saved dynamic-workflow script MAY live at `.claude/workflows/<name>.js` (plain JavaScript beginning with a literal `export const meta = { name, description }`; runs as `/<name>`). Ship one only when the blueprint justifies a script-held orchestration (see §5) — never as a substitute for the `CLAUDE.md` orchestrator.
- **Model & Project Settings:** MUST be written to `.claude/settings.json`, carrying the blueprint's `default_model` verbatim (e.g., `{"model": "opus"}`), the blueprint's optional `default_effort` as a top-level `effortLevel` (`low|medium|high|xhigh` — a project-settings `effortLevel` applies to every model, including Opus 5.5; `max` is not accepted there), plus any guard hooks (see §4). A top-level `effortLevel` in the operator's USER settings file does NOT reach Opus 5.5 or later models, so generated READMEs point operators to the project/local settings file or to the per-model `modelSettings` map (e.g. `{"modelSettings": {"claude-opus-5-5": {"effortLevel": "high"}}}`; `max` is not accepted there either). An operator-side `maxEffortLevel` cap (≥ 2.1.267) is documented in the generated README, never emitted by the generator.
- **Tooling (MCP):** Project-scoped MCP servers MUST be written to `<project-root>/.mcp.json` (NOT inside `.claude/`). Only add MCP servers for capabilities the native tools lack. Prefer the explicit `enabledMcpjsonServers` allowlist over `enableAllProjectMcpServers: true` in settings — trust decisions must be visible.

## 2. File Formats (CRITICAL)
- **`CLAUDE.md` MUST NOT contain YAML frontmatter.** It is plain markdown. Model configuration lives in `.claude/settings.json`.
- **Every `.claude/agents/<name>.md` MUST begin with a YAML frontmatter block.** Only `name` and `description` are required by Claude Code; everything else is optional:

```yaml
---
name: agent-name
description: Use this agent to <action-oriented trigger description — Claude Code uses this for automatic delegation>.
tools: Read, Grep, Glob
model: sonnet
---
```

- `name` (REQUIRED) SHOULD match the filename (without `.md`) — house convention for auditability; Claude Code itself identifies agents by `name`, not filename. Names containing `:` are rejected by Claude Code (≥ 2.1.218).
- `description` (REQUIRED) MUST be action-oriented ("Use this agent to/when ...") so the orchestrator can auto-delegate correctly. For agents that should trigger without being named explicitly, include the officially recommended phrase "use PROACTIVELY" (e.g., "Use PROACTIVELY after code changes").
- `tools` MUST be a least-privilege, comma-separated allowlist of real Claude Code tools: `Read`, `Write`, `Edit`, `Bash`, `Glob`, `Grep`, `WebSearch`, `WebFetch` (plus MCP tool names when required — a single tool as `mcp__<server>__<tool>`, or a whole server as `mcp__<server>__*`). This list is enforced by Claude Code — it is the swarm's actual security boundary. Read-only analysts get `Read, Grep, Glob`; researchers get `WebSearch, WebFetch`; only file-producing workers get `Write`/`Edit`; only command-running workers get `Bash`. Two coordination tools are governed by the same allowlist and are NEVER granted by default: `Agent` (nested delegation) and `SendMessage` (peer/parent messaging, see §5). In a subagent definition the `Agent(<subagent-type>)` type list is ignored: any `Agent` grant lets the worker spawn every subagent type up to the depth limit (§5), because the list is honoured only for an agent run as the main thread with `claude --agent`. A worker that must not delegate therefore lacks `Agent`, and a blueprint that must keep a type out of nested delegation adds a `permissions.deny` entry such as `"Agent(<name>)"` to `settings.json` (it applies to the whole session). If `tools` is omitted, the agent inherits ALL tools — including `Agent` and `SendMessage` — so omission is only acceptable with an explicit justification in the blueprint. MCP tool search is on by default (MCP definitions are deferred and loaded through the `ToolSearch` tool), and reported issues describe subagents losing deferred tools — anthropics/claude-code#79728 (an explicit `tools:` allowlist silently drops `ToolSearch` and all MCP tools when the MCP server is unavailable at spawn; closed as stale on 2026-10-10 without a fix) and anthropics/claude-code#90085 (deferred built-in tools unreachable from subagents; open); a probe on 2.1.284 (2026-09-29) confirmed that an allowlist which includes `ToolSearch` loads and calls them. Therefore any agent whose `tools` lists an `mcp__` entry MUST also list `ToolSearch`, and its body names a native fallback (e.g. `WebSearch`/`WebFetch`) for when the MCP tool is unavailable.
- **Roster size guard:** the combined `description` text of all custom agents in a workspace must stay under 15,000 tokens (Claude Code warns at startup beyond that); keep descriptions to one or two trigger sentences. Files MUST be saved as UTF-8 without a byte-order mark (BOM-prefixed agent, skill, and command files were silently ignored before v2.1.239).
- `model` MUST be a Claude Code alias per the Model Routing Doctrine below or `inherit` (the default). Full model version strings are forbidden by house doctrine (they break the future-proof alias routing — Rule 08 enforces the same restriction at blueprint level), even though Claude Code itself would accept them. The sole exception is the `model` field of `prompt`/`agent` hooks (see §4).
- **Advanced optional keys (all officially documented — use when the role justifies them, never reflexively):**
  - `disallowedTools:` — deny-list subtracted from the inherited/specified tools.
  - `effort:` — reasoning depth (`low`, `medium`, `high`, `xhigh`, `max`); applies while this agent runs, overriding the session level (never above a `maxEffortLevel` cap). A per-invocation `effort` parameter on the Agent tool (≥ 2.1.292) overrides this key in turn and persists when the agent is resumed; only `CLAUDE_CODE_EFFORT_LEVEL` outranks both. With no `effort` key the agent inherits the session level; the session default is `high` on every model that supports effort EXCEPT Opus 5.5, Sonnet 5.5 and Haiku 5.5, whose official default is `medium` (and Opus 4.7, which defaults to `xhigh`) — so an `opus`, `sonnet` or `haiku` agent on the Anthropic API with no `effort` key (and no project `effortLevel`) runs at `medium`. Effort support is per model, not per alias: Haiku 5.5 supports every level, but Haiku 4.5 — what `haiku` still resolves to on Claude Platform on AWS, Amazon Bedrock, Google Cloud's Agent Platform and Microsoft Foundry — and Sonnet 4.5 — what `sonnet` resolves to on Bedrock, Google Cloud and Foundry — do not support effort at all, and on Foundry `opus` resolves to Opus 4.6, where `xhigh` runs as `high`. Where effort is unsupported an `effort` key simply has no effect: a probe on 2.1.296 (2026-10-12) ran a subagent defined with `model: claude-haiku-4-5` and `effort: low` to completion with no error. So every tier follows the same effort rules (§7), and the generated README notes that `effort` keys are inert on providers where the alias resolves to a model without effort support. The official guidance on `max` is that it "may show diminishing returns and is prone to overthinking, so test before adopting it broadly", so it is FORBIDDEN in generated swarms (see §7 tier budget).
  - `isolation: worktree` — runs the agent in a temporary git worktree; assign it to agents that write files *inside the same git repository* in parallel with other writers. (Note: a worktree isolates the CURRENT repo only — it does not protect writes to paths outside the repo, which is why HiveSmith's own parallel Step-3 writers, who write distinct files into the target workspace, deliberately do not use it.) The worktree branches from the repository's default branch, not the caller's `HEAD`, unless settings set `"worktree": {"baseRef": "head"}`, and it holds only tracked files; a swarm whose parallel writers must build on in-progress branch work ships that setting, and its orchestrator commits shared state before spawning them.
  - `permissionMode:` — `default`, `acceptEdits`, `auto`, `dontAsk`, `bypassPermissions`, or `plan` (`manual` is accepted as an alias of `default` on Claude Code ≥ 2.1.200); never generate `bypassPermissions` without explicit human approval.
  - `maxTurns:` — hard cap on agentic turns for runaway protection; assign it to loop-prone workers (open-ended researchers, repo scanners). Since v2.1.246 a subagent that hits the cap returns its output marked **partial**, and the orchestrator can resume it with `SendMessage` — so a cap is a checkpoint, not a data loss.
  - `skills:` — skill names preloaded (full content) into the agent's context at startup.
  - `mcpServers:` — per-agent MCP servers (named references or inline configs). Inline definitions in a project agent file load only after the operator accepts the workspace-trust dialog for that folder interactively; a `claude -p` or SDK session does not count (≥ 2.1.238), so in a never-trusted folder they are silently skipped. Prefer named references to servers in `.mcp.json`.
  - `hooks:` — lifecycle hooks scoped to this agent (see §4).
  - `memory:` — persistent memory scope (`user`, `project`, or `local`) for cross-session learning; assign it to agents whose judgment improves by accumulating lessons across runs. It automatically enables `Read`, `Write` and `Edit`, and the docs do not limit them to the memory directory, so an agent given `memory:` is no longer read-only by its allowlist; weigh that before giving it to a reviewer.
  - `background: true` — always run this agent as a background task, even when the caller needs its result immediately.
  - `initialPrompt:` — auto-submitted first user turn when the agent runs as the main session agent (via `--agent` or the `agent` setting); irrelevant for orchestrator-invoked workers.
  - `color:` — display color in the task list (`red`, `blue`, `green`, `yellow`, `purple`, `orange`, `pink`, `cyan`; cosmetic).
  - `omitClaudeMd: true` — (≥ 2.1.271) launches the agent WITHOUT the user, project and local `CLAUDE.md` files (managed policy files still load). Only for agents that carry their entire brief in the delegation prompt and must not see project memory (e.g. an adversarial fresh-context reviewer); never on a worker that relies on the swarm's `CLAUDE.md`/rules for its constraints.
  - `experimental:` — a nested map, currently holding only `cacheTtl: "5m" | "1h"` (per-agent prompt-cache lifetime, ≥ 2.1.248). It MUST be written nested (`experimental:\n  cacheTtl: "1h"`), never as a top-level `cacheTtl` key. Justified only for long-running agents whose cache would otherwise expire between turns.
  - `autoCompactWindow:` — (≥ 2.1.296; in the changelog, not yet in the sub-agents frontmatter table) an integer token count, 100000 to 1000000, at which this subagent compacts its own conversation. It can only lower the window the subagent would otherwise inherit. Use it only for long-running workers that should compact earlier than the main window.

> **FORBIDDEN FIELDS:** `max_output_tokens`, `enable_write_tools`, `enable_mcp_tools`, `enable_subagent_tools`, `planning-mode`. These are foreign (Antigravity) fields. Claude Code does not recognize them; emitting them is a schema violation that `qa-validator` MUST reject. Any key outside the documented set above is likewise a violation.

## 3. Context Inheritance & Anti-Duplication (CRITICAL)
Custom subagents automatically load the FULL memory hierarchy at startup — `~/.claude/CLAUDE.md`, the project `CLAUDE.md`, and every auto-loaded `.claude/rules/*.md` (official: sub-agents.md "What loads at startup"; only the built-in Explore and Plan agents skip it). Therefore:
- **NEVER copy global rules into individual agent bodies** — neither in HiveSmith's own roster nor in generated swarms. Duplicated text drifts out of sync over time and produces contradictions; the rules directory is the single source of truth that every agent already sees.
- Agent bodies contain ONLY role-specific content: responsibilities, constraints unique to the role, error handling, and output format. A one-line pointer ("per Rule 03", "per the Destructive Action Barrier") is acceptable where emphasis genuinely helps.
- What subagents do NOT inherit: the parent's conversation history, the parent's auto memory, the parent's output style, and the parent's context-window size (a subagent's window is sized by its OWN model). Task-specific context (the Manifesto, file paths, prior decisions) must therefore still be passed explicitly in every delegation prompt.

## 4. Hooks: The Deterministic Enforcement Layer
`CLAUDE.md` and `.claude/rules/` are **advisory** — they are delivered as context, not enforced by the harness. Any constraint that must hold with ZERO exceptions (destructive-command bans, secret-file protection, mandatory format gates) MUST additionally be enforced by the harness — a hook or a `permissions.deny` rule (secret files use `Read` deny rules, Rule 02 §4) — because both act deterministically outside the model's discretion.
- **Where (placement is security-relevant):** project-wide hooks in `.claude/settings.json`; role-scoped hooks in the agent's `hooks:` frontmatter. Settings-file hooks run inside every subagent too (the hook input then carries `agent_id`/`agent_type`) and fire in headless `claude -p` runs. Agent-frontmatter hooks run only while that agent is active, a `Stop` hook declared there becomes `SubagentStop`, and — critically — they are registered only after the operator has accepted the workspace-trust dialog for that folder; **a `-p` session never counts as accepting it**. Therefore every guard that must hold unconditionally lives in `.claude/settings.json`, never only in agent frontmatter.
- **Key events (33 official events as of 2.1.296 — this is the swarm-relevant subset; consult the official hooks reference before assuming an event does not exist):** `PreToolUse` (gate/deny a tool call before it runs — exit code 2 or `"permissionDecision": "deny"` blocks it; `"allow"` pre-approves it; `updatedInput` rewrites its arguments), `PostToolUse`/`PostToolUseFailure`, `PermissionRequest`/`PermissionDenied` (`PermissionRequest` supports `command`, `http`, `mcp_tool` and `prompt` handlers but not `agent` — an `agent`-type handler there no longer runs since 2.1.280; only a `command` or `http` hook can return the allow/deny decision object), `SubagentStart`/`SubagentStop` (matcher = agent type — the natural place for per-role verification gates), `Stop` (gate turn-end on a passing check — note: Claude Code caps Stop-hook continuations at 8 consecutive blocks (`CLAUDE_CODE_STOP_HOOK_BLOCK_CAP`) and then lets the turn end, so a Stop hook is a backstop, not the sole defense), `PreModelSwitch`/`PostModelSwitch` (≥ 2.1.251; block or annotate a model change), `PreCompact`/`PostCompact`, `InstructionsLoaded`, `DirectoryAdded` (≥ 2.1.220), `WorktreeCreate`/`WorktreeRemove`, `SessionStart`/`SessionEnd`, `UserPromptSubmit` (plain stdout or `additionalContext` is injected as context — write it as factual statements, never as imperative out-of-band "system" commands, which the official hooks reference warns can trigger Claude's prompt-injection defenses; the same applies to every hook that injects context, e.g. `SessionStart` or `PostToolUse` `additionalContext`).
- **Hook types:** `command` (shell script — the default workhorse), `prompt` (single-turn LLM evaluation, Haiku by default, 30 s default timeout), `agent` (multi-turn verification subagent with tool access — experimental), `http` (POST to an endpoint), `mcp_tool` (call a connected MCP tool). A `prompt`/`agent` hook normally omits `model` and runs on the documented fast default. When a specific model is needed, pin a full model ID (e.g. `claude-sonnet-5-5` on the Anthropic API) rather than an alias: the docs do not say alias resolution applies there, and a live probe on 2.1.284 (2026-09-29) found that a `PreToolUse` prompt hook with `"model": "sonnet"` never took effect — the tool call went through as if the hook did not exist, with no error shown — while the same hook with `"model": "claude-sonnet-5-5"` ran and blocked as instructed, and model IDs are provider-specific, so the generated README states which provider the ID assumes. This is the one exception to the alias-only rule. Every handler accepts an optional `if:` filter in permission-rule syntax (e.g. `"if": "Bash(rm *)"`) that narrows a tool-event hook beyond the `matcher`. The filter is best-effort (the docs: "use the permission system rather than a hook to enforce a hard allow or deny"), so a guard hook never uses it and inspects the whole command itself. Handlers also take `timeout` (seconds), `statusMessage` and, on `command` and `http` hooks (≥ 2.1.295), `onFailure`: with the default `"continue"`, a hook that cannot start, crashes, times out or exits with an unexpected code lets the action through, so every guard hook sets `"onFailure": "block"` and exits only 0 or 2. Path placeholders: `${CLAUDE_PROJECT_DIR}` (the session's start directory — read `cwd` from the hook input inside worktrees).
- Generated swarms with a Destructive Action Barrier MUST ship a `PreToolUse` deny hook for the domain's destructive command patterns alongside the prose rule (matcher, failure mode and companion layers: Rule 02 §4). Do NOT rely on `defaultMode` in a generated project `settings.json` for anything security-relevant: `bypassPermissions` and `auto` set there are ignored by Claude Code (≥ 2.1.257 — they must come from user/managed settings or the CLI flag).

## 5. Coordination: Hub-and-Spoke by Design, Not by Runtime Limitation
Hub-and-spoke through the orchestrator is the DEFAULT topology of every generated swarm — but it is now a design decision enforced by the `tools:` allowlist, not a runtime impossibility. The facts (official, ≥ 2.1.206): a subagent whose `tools` include `SendMessage` receives a **sibling roster** (`main` plus every named agent in the session) and can message its parent or any named sibling; a completed subagent that receives a `SendMessage` auto-resumes in the background without a new `Agent` call; and the orchestrator can resume any subagent (including one stopped at `maxTurns`) the same way. Doctrine:
- Workers get `SendMessage` ONLY when the blueprint names the peer relationship and its purpose (e.g. an implementer returning a clarification to a spec-owner); otherwise omit it, and the roster never appears. A generated `CLAUDE.md` never assumes peer messaging that the allowlists do not grant.
- The orchestrator itself keeps `SendMessage` — resuming a partial `maxTurns` result is the canonical use.
- **Agent Teams** (still experimental; requires `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`) remain the mechanism for a lead supervising long-running peers with a shared task list. Propose them only with explicit justification in the blueprint, and mark the swarm as depending on an experimental feature.
- **Dynamic Workflows** (GA on paid plans; `.claude/workflows/<name>.js`, see §1) move the plan into a script: `agent()`, `parallel()`, `pipeline()`, `phase()` orchestrate dozens to hundreds of subagents per run (workflow-runtime caps, separate from the subagent limits below: 16 concurrent by default — raise with `CLAUDE_CODE_WORKFLOW_MAX_CONCURRENT_AGENTS`, 1–256 —, 1,000 agents per run, 4,096 items per `parallel`/`pipeline` call; the advisory size guideline defaults to "medium" = fewer than 10 agents per run, "small" on Pro, adjustable via the `workflowSizeGuideline` setting), intermediate results stay in script variables instead of the orchestrator's context, and a run is resumable within the session. Blueprint a workflow when the target swarm's core job is a repeatable fan-out with cross-verification (an N-file audit, a bulk migration, adversarially-verified research); the `CLAUDE.md` orchestrator still owns judgment, the script owns the loop. Workflow agents reference the same `.claude/agents/*.md` definitions. A run that hits the operator's usage limit pauses and resumes automatically after the reset (≥ 2.1.271), but only in an interactive session signed in with a claude.ai subscription, with `autoContinueAtUsageLimit` on, a reset within 24 hours and at most two waits per run; otherwise the affected agent fails. Since 2.1.277 every subagent result reaches the caller under an explicit "subagent output" header, which helps the orchestrator attribute text to its source — but it is presentation, not an injection guarantee: Rule 04 still applies to everything a worker returns.

Runtime behaviors to design around (Claude Code ≥ 2.1.198): subagents run in the **background by default** (in interactive sessions with fork mode on — the default — every subagent is backgrounded and the caller cannot ask for the foreground) — every subagent loses `AskUserQuestion`, the plan-mode tools and `Workflow` (so only the main session can start a dynamic workflow), and a background subagent keeps a fixed built-in set (including `Read`, `Grep`, `Glob`, `Bash`, `Edit`, `Write`, `WebFetch`, `WebSearch`, `ToolSearch` and `SendMessage`) plus every MCP tool, so backgrounded researchers keep their full research capability; a subagent cut off mid-stream by a network or server error auto-continues (≥ 2.1.257); and subagents **inherit the main session's extended-thinking setting** — there is no per-agent thinking override.

Hard limits: default **20 concurrently-running subagents** (`CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`) and `CLAUDE_CODE_MAX_TOOL_USE_CONCURRENCY` — the "maximum number of read-only tools and subagents that can execute in parallel", **default 10** — size fan-outs within these. There is NO per-session spawn budget: the former 200-spawn cap (`CLAUDE_CODE_MAX_SUBAGENTS_PER_SESSION`) was removed in v2.1.224 and the variable is now a no-op, so never emit it or design around it. Subagents can themselves spawn nested subagents to a default **depth of 3** (`CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`; at the limit the `Agent` tool is withheld); strict hub-and-spoke designs enforce no-nested-delegation by omitting `Agent` from worker allowlists (or pin the env var to 1) rather than assume the runtime forbids it. One deliberate exception to context isolation exists: **`fork` subagents** (≥ 2.1.221) inherit the parent's full conversation and prompt cache — useful for checkpoint-style continuations of the orchestrator itself, but NEVER a substitute for the explicit Manifesto when delegating to named worker agents.

## 6. Direct File Writes
Do NOT output massive markdown templates inside JSON strings when communicating. If your job is to generate a file, write it directly to disk. Prefer the native `Write`/`Edit` tools over `Bash` heredocs/redirection for file content — they are permission-checked and path-scoped rules load on them; `Bash` is for directory creation (`mkdir -p`) and verification commands. Checkpointing tracks native edits in the main conversation only: `/rewind` does not restore files a subagent wrote, so a worker's output is reverted with git or by re-running its step.

## 7. Dynamic Model Routing (Canonical Doctrine)
Do NOT hardcode specific model version strings in your architectural designs. Use tier-based aliases. This table is the ONE canonical tier mapping — `CLAUDE.md` and all agents defer to it:
- **`fable` — Frontier reasoning:** long-horizon autonomous work, orchestration-critical creation and architecture (the roles where a reasoning failure poisons everything downstream).
- **`opus` — Complex agentic coding & enterprise work:** Anthropic's default recommendation ("If you're unsure which model to use, start with Claude Opus 5.5 for most workloads" — platform.claude.com models overview; Opus 5.5 as of 2026-09-22: 1M context, Fable-5.1-level results on most work at 40% lower cost than Opus 5, official default effort `medium`); the strong alternative when `fable` is unavailable or not warranted.
- **`sonnet` — Balanced default:** research, synthesis, integration — the best speed/intelligence combination for most production work (Sonnet 5.5 as of 2026-09-28 on the Anthropic API: 1M context, $2/$10 per MTok, requires Claude Code ≥ 2.1.284, official default effort `medium` in Claude Code; on Bedrock, Google Cloud and Foundry the alias still resolves to Sonnet 4.5, on Claude Platform on AWS to Sonnet 4.6).
- **`haiku` — Narrow, high-volume, fast tasks:** rapid scanning, classification, mechanical validation in generated swarms where the domain's cost profile matters (Haiku 5.5 on the Anthropic API since Claude Code 2.1.293: 1M context, costs more per token on prompts longer than 100K tokens, official default effort `medium`; on Claude Platform on AWS, Bedrock, Google Cloud and Foundry the alias still resolves to Haiku 4.5, which has no effort support).
- **`inherit` — Match the caller:** when a worker should always run on whatever model the orchestrator is using.

Further official aliases exist (≥ 2.1.219): `best` (the latest Fable where available, else the same model as `opus`), `opusplan` (Opus while planning, Sonnet for execution), `sonnet[1m]`/`opus[1m]` (1M-token context variants — a no-op where the alias already resolves to a native-1M model such as Sonnet 5.5 or Fable 5.1), and the special value `default` (clears an override back to the account default). House doctrine: generated swarms route ONLY through the five canonical tiers above — the extras are session-level conveniences for human operators, never blueprint or frontmatter values (Rule 08's `model` enum stays `fable|opus|sonnet|haiku|inherit`). Operators can re-route a whole swarm without editing files: `CLAUDE_CODE_SUBAGENT_MODEL` sets the default for agents whose definition has no `model` (a definition's `model`, including `inherit`, wins), and the boolean `CLAUDE_CODE_SUBAGENT_MODEL_FORCE=1` (≥ 2.1.257) makes that model override every definition (set alone, it forces the main conversation's model) — generated READMEs MUST mention both, with the exact `env` block shape. A swarm that ships a workflow also mentions `CLAUDE_CODE_WORKFLOW_SUBAGENT_MODEL` (≥ 2.1.296, changelog-documented), which runs every workflow agent on one model while other subagents keep theirs.

**Generated-swarm tier & effort budget (CRITICAL — binds `domain-architect` and `qa-validator`).** HiveSmith's OWN roster is deliberately generously tiered (see CLAUDE.md "Model routing") — it is a creator, and output quality outranks cost. The swarms it GENERATES run in production on their operators' subscriptions, where a uniformly frontier-tiered roster exhausts a rate-limit window in one run. Therefore, in every generated swarm:
- The orchestrator (`default_model`, written to `settings.json`) is `opus` by default — Anthropic's recommended starting tier for most workloads; `fable` there only when the domain is genuinely frontier-hard and the blueprint says why.
- `sonnet` is the default worker tier; `haiku` is preferred for mechanical, high-volume read-and-report roles (scanners, classifiers, log and test-output readers, lookups and summaries). A mechanical edit across many files stays on the tier that writes the swarm's code, at `effort: low` — Anthropic: "Move down to Sonnet or Haiku for lookups, not for writing code" (claude.dev/blog/what-a-task-costs-on-opus-5-5).
- `opus` for a worker is reserved for roles doing complex agentic implementation, and each such assignment carries benchmark `tier_evidence` in the blueprint.
- `fable` is capped at `default_model` plus at most ONE architect-class agent whose reasoning failure would poison everything downstream — never a whole tier of workers (`model: inherit` agents count as whatever `default_model` is).
- `effort`: an agent with no `effort` key inherits the session level, and with no `default_effort` that level is the official model default — `medium` on `opus` (Opus 5.5), `sonnet` (Sonnet 5.5) and `haiku` (Haiku 5.5, on the Anthropic API) and `high` on `fable` — Anthropic's deliberate defaults, which resolve routine tasks with fewer steps and tokens. That is right for implementers and synthesizers, and wrong for two role classes, which therefore MUST set `effort: high` in frontmatter on every tier, `haiku` included: **verification/QA/reviewer roles and research roles**. The Sonnet 5.5 prompting guide (platform.claude.com) states that at low and medium, "on long agentic tasks, it's more likely to stop and check in with the user before it finishes", and at low it "can skip verifying a change" — exactly the failure a verifier or researcher exists to prevent. Mechanical, high-volume `haiku` roles (scanners, classifiers, log readers) SHOULD set `effort: low` and keep their prompts short — the settings reference describes `low` as "the least reasoning, for short, scoped, latency-sensitive tasks that aren't intelligence-sensitive", the Haiku 5.5 guide warns that at `low` a long agent prompt makes it more likely to skip a search or stop early, and that at `low` and `medium` it sometimes reports a code change as done without running a check, and the orchestrator reviews each result they return; omitted, they run at Haiku 5.5's default `medium`. Where an alias resolves to a model without effort support (§2), these keys are inert and the role runs without effort control. A generated orchestrator never passes a per-invocation `effort` below `high` to a verification or research role, since that parameter overrides the frontmatter (§2). `xhigh` only with a stated, measured quality gain (the guide: "Reserve xhigh and max for work where you've measured a quality gain"); `max` is FORBIDDEN in generated frontmatter, `settings.json` and blueprints (official guidance: diminishing returns, prone to overthinking; settings keys do not even accept it). When the domain's judgment load genuinely needs the `opus` orchestrator at `high`, the blueprint sets `default_effort: high` (written to `settings.json` `effortLevel`) with a one-line reason.
