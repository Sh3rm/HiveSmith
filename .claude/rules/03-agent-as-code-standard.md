# The "Agent as Code" Standard

Every single sub-agent and orchestrator generated in this workspace MUST strictly adhere to the following physical and structural standards. These are Claude Code's real, documented conventions (last verified against Claude Code v2.1.280 and the official docs on 2026-09-23) — deviation produces a swarm that Claude Code silently fails to load. This applies to ALL generated swarms.

> **CANONICAL SOURCE:** This file is the single source of truth for the Claude Code file/frontmatter schema and the Model Routing Doctrine. Other files (CLAUDE.md, agent bodies) MUST reference this rule instead of restating its lists — duplicated copies drift out of sync and produce contradictions.

## 1. Physical Directory Structure
- **Orchestrator (`CLAUDE.md`):** MUST be written directly to the project root directory (e.g., `<project-root>/CLAUDE.md`). Plain markdown — Claude Code loads it automatically as project memory (since v2.1.277 a project with NO `CLAUDE.md` falls back to `AGENTS.md`; generated swarms always ship `CLAUDE.md`, never rely on the fallback). It may import auxiliary files with the `@path/to/file` syntax (expanded at launch, up to 4 hops) to stay modular.
- **Sub-Agents:** MUST be written to `.claude/agents/<agent-name>.md` — one file per agent. Never write agent folders to the project root, and never use the `.claude/skills/<name>/SKILL.md` layout for worker personas (skills are instruction packs, not isolated agents).
- **Global Rules:** MUST be written to `.claude/rules/<rule-name>.md`. Claude Code auto-loads every markdown file in this directory at startup. Scope a rule to file patterns with `paths:` frontmatter (glob patterns, brace expansion supported) when it only applies to part of the tree — path-scoped rules load only when matching files are read, keeping sessions lean.
- **Skills (optional):** Reusable multi-step procedures or domain playbooks MAY be packaged under `.claude/skills/` and preloaded into a specific agent via its `skills:` frontmatter. Skills are for on-demand procedural knowledge; always-mandatory standards belong in `.claude/rules/` (auto-loaded), never in skills.
- **Workflows (optional):** A saved dynamic-workflow script MAY live at `.claude/workflows/<name>.js` (plain JavaScript beginning with a literal `export const meta = { name, description }`; runs as `/<name>`). Ship one only when the blueprint justifies a script-held orchestration (see §5) — never as a substitute for the `CLAUDE.md` orchestrator.
- **Model & Project Settings:** MUST be written to `.claude/settings.json`, carrying the blueprint's `default_model` verbatim (e.g., `{"model": "opus"}`), the blueprint's optional `default_effort` as a top-level `effortLevel` (`low|medium|high|xhigh` — a project-settings `effortLevel` applies to every model, including Opus 5.5; `max` is not accepted there), plus any guard hooks (see §4). An operator-side `maxEffortLevel` cap (≥ 2.1.267) is documented in the generated README, never emitted by the generator.
- **Tooling (MCP):** Project-scoped MCP servers MUST be written to `<project-root>/.mcp.json` (NOT inside `.claude/`). Only add MCP servers for capabilities the native tools lack. Prefer the explicit `enabledMcpjsonServers` allowlist over `enableAllProjectMcpServers: true` in settings — trust decisions must be visible.

## 2. File Formats (CRITICAL)
- **`CLAUDE.md` MUST NOT contain YAML frontmatter.** It is plain markdown. Model configuration lives in `.claude/settings.json`.
- **Every `.claude/agents/<name>.md` MUST begin with a YAML frontmatter block.** Only `name` and `description` are required by Claude Code; everything else is optional:

```yaml
---
name: agent-name
description: Use this agent to <action-oriented trigger description — Claude Code uses this for automatic delegation>.
tools: Read, Grep, Glob
model: sonnet
---
```

- `name` (REQUIRED) SHOULD match the filename (without `.md`) — house convention for auditability; Claude Code itself identifies agents by `name`, not filename. Names containing `:` are rejected by Claude Code (≥ 2.1.218).
- `description` (REQUIRED) MUST be action-oriented ("Use this agent to/when ...") so the orchestrator can auto-delegate correctly. For agents that should trigger without being named explicitly, include the officially recommended phrase "use PROACTIVELY" (e.g., "Use PROACTIVELY after code changes").
- `tools` MUST be a least-privilege, comma-separated allowlist of real Claude Code tools: `Read`, `Write`, `Edit`, `Bash`, `Glob`, `Grep`, `WebSearch`, `WebFetch` (plus MCP tool names when required — a single tool as `mcp__<server>__<tool>`, or a whole server as `mcp__<server>__*`). This list is enforced by Claude Code — it is the swarm's actual security boundary. Read-only analysts get `Read, Grep, Glob`; researchers get `WebSearch, WebFetch`; only file-producing workers get `Write`/`Edit`; only command-running workers get `Bash`. Two coordination tools are governed by the same allowlist and are NEVER granted by default: `Agent` (nested delegation — restrict it to named types with the `Agent(<subagent-type>)` syntax when a worker must delegate) and `SendMessage` (peer/parent messaging, see §5). If `tools` is omitted, the agent inherits ALL tools — including `Agent` and `SendMessage` — so omission is only acceptable with an explicit justification in the blueprint.
- **Roster size guard:** the combined `description` text of all custom agents in a workspace must stay under 15,000 tokens (Claude Code warns at startup beyond that); keep descriptions to one or two trigger sentences. Files MUST be saved as UTF-8 without a byte-order mark (BOM-prefixed agent, skill, and command files were silently ignored before v2.1.239).
- `model` MUST be a Claude Code alias per the Model Routing Doctrine below or `inherit` (the default). Full model version strings are forbidden by house doctrine (they break the future-proof alias routing — Rule 08 enforces the same restriction at blueprint level), even though Claude Code itself would accept them.
- **Advanced optional keys (all officially documented — use when the role justifies them, never reflexively):**
  - `disallowedTools:` — deny-list subtracted from the inherited/specified tools.
  - `effort:` — reasoning depth (`low`, `medium`, `high`, `xhigh`, `max`); applies while this agent runs, overriding the session level (but not `CLAUDE_CODE_EFFORT_LEVEL`, and never above a `maxEffortLevel` cap). Model defaults: `high` on every current model EXCEPT Opus 5.5, whose official default is `medium` — so an `opus` agent with no `effort` key runs at `medium`. The official guidance on `max` is "may show diminishing returns and is prone to overthinking — test before adopting broadly", so it is FORBIDDEN in generated swarms (see §7 tier budget).
  - `isolation: worktree` — runs the agent in a temporary git worktree; assign it to agents that write files *inside the same git repository* in parallel with other writers. (Note: a worktree isolates the CURRENT repo only — it does not protect writes to paths outside the repo, which is why HiveSmith's own parallel Step-3 writers, who write distinct files into the target workspace, deliberately do not use it.)
  - `permissionMode:` — `default`, `acceptEdits`, `auto`, `dontAsk`, `bypassPermissions`, or `plan` (`manual` is accepted as an alias of `default` on Claude Code ≥ 2.1.200); never generate `bypassPermissions` without explicit human approval.
  - `maxTurns:` — hard cap on agentic turns for runaway protection; assign it to loop-prone workers (open-ended researchers, repo scanners). Since v2.1.246 a subagent that hits the cap returns its output marked **partial**, and the orchestrator can resume it with `SendMessage` — so a cap is a checkpoint, not a data loss.
  - `skills:` — skill names preloaded (full content) into the agent's context at startup.
  - `mcpServers:` — per-agent MCP servers (named references or inline configs).
  - `hooks:` — lifecycle hooks scoped to this agent (see §4).
  - `memory:` — persistent memory scope (`user`, `project`, or `local`) for cross-session learning; assign it to agents whose judgment improves by accumulating lessons across runs.
  - `background: true` — always run this agent as a background task, even when the caller needs its result immediately.
  - `initialPrompt:` — auto-submitted first user turn when the agent runs as the main session agent (via `--agent` or the `agent` setting); irrelevant for orchestrator-invoked workers.
  - `color:` — display color in the task list (`red`, `blue`, `green`, `yellow`, `purple`, `orange`, `pink`, `cyan`; cosmetic).
  - `omitClaudeMd: true` — (≥ 2.1.271) launches the agent WITHOUT the user, project and local `CLAUDE.md` files (managed policy files still load). Only for agents that carry their entire brief in the delegation prompt and must not see project memory (e.g. an adversarial fresh-context reviewer); never on a worker that relies on the swarm's `CLAUDE.md`/rules for its constraints.
  - `experimental:` — a nested map, currently holding only `cacheTtl: "5m" | "1h"` (per-agent prompt-cache lifetime, ≥ 2.1.248). It MUST be written nested (`experimental:\n  cacheTtl: "1h"`), never as a top-level `cacheTtl` key. Justified only for long-running agents whose cache would otherwise expire between turns.

> **FORBIDDEN FIELDS:** `max_output_tokens`, `enable_write_tools`, `enable_mcp_tools`, `enable_subagent_tools`, `planning-mode`. These are foreign (Antigravity) fields. Claude Code does not recognize them; emitting them is a schema violation that `qa-validator` MUST reject. Any key outside the documented set above is likewise a violation.

## 3. Context Inheritance & Anti-Duplication (CRITICAL)
Custom subagents automatically load the FULL memory hierarchy at startup — `~/.claude/CLAUDE.md`, the project `CLAUDE.md`, and every auto-loaded `.claude/rules/*.md` (official: sub-agents.md "What loads at startup"; only the built-in Explore and Plan agents skip it). Therefore:
- **NEVER copy global rules into individual agent bodies** — neither in HiveSmith's own roster nor in generated swarms. Duplicated text drifts out of sync over time and produces contradictions; the rules directory is the single source of truth that every agent already sees.
- Agent bodies contain ONLY role-specific content: responsibilities, constraints unique to the role, error handling, and output format. A one-line pointer ("per Rule 03", "per the Destructive Action Barrier") is acceptable where emphasis genuinely helps.
- What subagents do NOT inherit: the parent's conversation history, the parent's auto memory, the parent's output style, and the parent's context-window size (a subagent's window is sized by its OWN model). Task-specific context (the Manifesto, file paths, prior decisions) must therefore still be passed explicitly in every delegation prompt.

## 4. Hooks: The Deterministic Enforcement Layer
`CLAUDE.md` and `.claude/rules/` are **advisory** — they are delivered as context, not enforced by the harness. Any constraint that must hold with ZERO exceptions (destructive-command bans, secret-file protection, mandatory format gates) MUST additionally be implemented as a hook, because hooks execute deterministically outside the model's discretion.
- **Where (placement is security-relevant):** project-wide hooks in `.claude/settings.json`; role-scoped hooks in the agent's `hooks:` frontmatter. Settings-file hooks run inside every subagent too (the hook input then carries `agent_id`/`agent_type`) and fire in headless `claude -p` runs. Agent-frontmatter hooks run only while that agent is active, a `Stop` hook declared there becomes `SubagentStop`, and — critically — they are registered only after the operator has accepted the workspace-trust dialog for that folder; **a `-p` session never counts as accepting it**. Therefore every guard that must hold unconditionally lives in `.claude/settings.json`, never only in agent frontmatter.
- **Key events (33 official events as of 2.1.280 — this is the swarm-relevant subset; consult the official hooks reference before assuming an event does not exist):** `PreToolUse` (gate/deny a tool call before it runs — exit code 2 or `"permissionDecision": "deny"` blocks it; `"allow"` pre-approves it; `updatedInput` rewrites its arguments), `PostToolUse`/`PostToolUseFailure`, `PermissionRequest`/`PermissionDenied` (`PermissionRequest` accepts `command`/`http` handlers only — an `agent`-type handler there is rejected since 2.1.280), `SubagentStart`/`SubagentStop` (matcher = agent type — the natural place for per-role verification gates), `Stop` (gate turn-end on a passing check — note: Claude Code caps Stop-hook continuations at 8 consecutive blocks and then lets the turn end, so a Stop hook is a backstop, not the sole defense), `PreModelSwitch`/`PostModelSwitch` (≥ 2.1.251; block or annotate a model change), `PreCompact`/`PostCompact`, `InstructionsLoaded`, `DirectoryAdded` (≥ 2.1.220), `WorktreeCreate`/`WorktreeRemove`, `SessionStart`/`SessionEnd`.
- **Hook types:** `command` (shell script — the default workhorse), `prompt` (single-turn LLM evaluation, Haiku by default), `agent` (multi-turn verification subagent with tool access — experimental), `http` (POST to an endpoint), `mcp_tool` (call a connected MCP tool). Every handler accepts an optional `if:` filter in permission-rule syntax (e.g. `"if": "Bash(rm *)"`) that narrows a tool-event hook beyond the `matcher`, plus `timeout` (seconds) and `statusMessage`. Path placeholders: `${CLAUDE_PROJECT_DIR}` (the session's start directory — read `cwd` from the hook input inside worktrees).
- Generated swarms with a Destructive Action Barrier MUST ship a `PreToolUse` deny hook for the domain's destructive command patterns alongside the prose rule (see Rule 02). Do NOT rely on `defaultMode` in a generated project `settings.json` for anything security-relevant: `bypassPermissions` and `auto` set there are ignored by Claude Code (≥ 2.1.257 — they must come from user/managed settings or the CLI flag).

## 5. Coordination: Hub-and-Spoke by Design, Not by Runtime Limitation
Hub-and-spoke through the orchestrator is the DEFAULT topology of every generated swarm — but it is now a design decision enforced by the `tools:` allowlist, not a runtime impossibility. The facts (official, ≥ 2.1.206): a subagent whose `tools` include `SendMessage` receives a **sibling roster** (`main` plus every named agent in the session) and can message its parent or any named sibling; a completed subagent that receives a `SendMessage` auto-resumes in the background without a new `Agent` call; and the orchestrator can resume any subagent (including one stopped at `maxTurns`) the same way. Doctrine:
- Workers get `SendMessage` ONLY when the blueprint names the peer relationship and its purpose (e.g. an implementer returning a clarification to a spec-owner); otherwise omit it, and the roster never appears. A generated `CLAUDE.md` never assumes peer messaging that the allowlists do not grant.
- The orchestrator itself keeps `SendMessage` — resuming a partial `maxTurns` result is the canonical use.
- **Agent Teams** (still experimental; requires `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`) remain the mechanism for a lead supervising long-running peers with a shared task list. Propose them only with explicit justification in the blueprint, and mark the swarm as depending on an experimental feature.
- **Dynamic Workflows** (GA on paid plans; `.claude/workflows/<name>.js`, see §1) move the plan into a script: `agent()`, `parallel()`, `pipeline()`, `phase()` orchestrate dozens to hundreds of subagents per run (workflow-runtime caps, separate from the subagent limits below: 16 concurrent by default — raise with `CLAUDE_CODE_WORKFLOW_MAX_CONCURRENT_AGENTS`, 1–256 —, 1,000 agents per run, 4,096 items per `parallel`/`pipeline` call; the advisory size guideline defaults to "medium" = fewer than 10 agents per run, "small" on Pro, adjustable via the `workflowSizeGuideline` setting), intermediate results stay in script variables instead of the orchestrator's context, and a run is resumable within the session. Blueprint a workflow when the target swarm's core job is a repeatable fan-out with cross-verification (an N-file audit, a bulk migration, adversarially-verified research); the `CLAUDE.md` orchestrator still owns judgment, the script owns the loop. Workflow agents reference the same `.claude/agents/*.md` definitions. A run that hits the operator's usage limit pauses and resumes automatically after the reset (≥ 2.1.271). Since 2.1.277 every subagent result reaches the caller under an explicit "subagent output" header, which helps the orchestrator attribute text to its source — but it is presentation, not an injection guarantee: Rule 04 still applies to everything a worker returns.

Runtime behaviors to design around (Claude Code ≥ 2.1.198): subagents run in the **background by default** (in interactive sessions with fork mode on — the default — every subagent is backgrounded and the caller cannot ask for the foreground) — the background tool reduction concerns interactive facilities (Artifact, plan-mode tools), NOT `WebSearch`/`WebFetch`/MCP tools, so backgrounded researchers keep their full research capability; a subagent cut off mid-stream by a network or server error auto-continues (≥ 2.1.257); and subagents **inherit the main session's extended-thinking setting** — there is no per-agent thinking override.

Hard limits: default **20 concurrently-running subagents** (`CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`) and **200 subagent spawns per session** (`CLAUDE_CODE_MAX_SUBAGENTS_PER_SESSION`, introduced in v2.1.217 — `/clear` resets the budget) — size rosters and fan-outs within these. Subagents can themselves spawn nested subagents to a default **depth of 3** (`CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`; at the limit the `Agent` tool is withheld); strict hub-and-spoke designs enforce no-nested-delegation by omitting `Agent` from worker allowlists (or pin the env var to 1) rather than assume the runtime forbids it. One deliberate exception to context isolation exists: **`fork` subagents** (≥ 2.1.221) inherit the parent's full conversation and prompt cache — useful for checkpoint-style continuations of the orchestrator itself, but NEVER a substitute for the explicit Manifesto when delegating to named worker agents.

## 6. Direct File Writes
Do NOT output massive markdown templates inside JSON strings when communicating. If your job is to generate a file, write it directly to disk. Prefer the native `Write`/`Edit` tools over `Bash` heredocs/redirection for file content — native file tools are tracked by Claude Code's checkpointing, keeping every change reversible via `/rewind`; `Bash` is for directory creation (`mkdir -p`) and verification commands.

## 7. Dynamic Model Routing (Canonical Doctrine)
Do NOT hardcode specific model version strings in your architectural designs. Use tier-based aliases. This table is the ONE canonical tier mapping — `CLAUDE.md` and all agents defer to it:
- **`fable` — Frontier reasoning:** long-horizon autonomous work, orchestration-critical creation and architecture (the roles where a reasoning failure poisons everything downstream).
- **`opus` — Complex agentic coding & enterprise work:** Anthropic's official "start here" model for most workloads (Opus 5.5 as of 2026-09-22: 1M context, Fable-5.1-level results on most work at 40% lower cost than Opus 5, official default effort `medium`); the strong alternative when `fable` is unavailable or not warranted.
- **`sonnet` — Balanced default:** research, synthesis, integration — the best speed/intelligence combination for most production work.
- **`haiku` — Narrow, high-volume, fast tasks:** rapid scanning, classification, mechanical validation in generated swarms where the domain's cost profile matters.
- **`inherit` — Match the caller:** when a worker should always run on whatever model the orchestrator is using.

Further official aliases exist (≥ 2.1.219): `best` (the latest Fable where available, else the same model as `opus`), `opusplan` (Opus while planning, Sonnet for execution), `sonnet[1m]`/`opus[1m]` (1M-token context variants — a no-op where the alias already resolves to a native-1M model such as Sonnet 5 or Fable 5.1), and the special value `default` (clears an override back to the account default). House doctrine: generated swarms route ONLY through the five canonical tiers above — the extras are session-level conveniences for human operators, never blueprint or frontmatter values (Rule 08's `model` enum stays `fable|opus|sonnet|haiku|inherit`). Operators can re-route a whole swarm without editing files: `CLAUDE_CODE_SUBAGENT_MODEL` sets the default for agents whose definition has no `model` (a definition's `model`, including `inherit`, wins), and the boolean `CLAUDE_CODE_SUBAGENT_MODEL_FORCE=1` (≥ 2.1.257) makes that model override every definition (set alone, it forces the main conversation's model) — generated READMEs MUST mention both, with the exact `env` block shape.

**Generated-swarm tier & effort budget (CRITICAL — binds `domain-architect` and `qa-validator`).** HiveSmith's OWN roster is deliberately generously tiered (see CLAUDE.md "Self-Routing") — it is a creator, and output quality outranks cost. The swarms it GENERATES run in production on their operators' subscriptions, where a uniformly frontier-tiered roster exhausts a rate-limit window in one run. Therefore, in every generated swarm:
- The orchestrator (`default_model`, written to `settings.json`) is `opus` by default — the official "start here" tier for complex agentic work; `fable` there only when the domain is genuinely frontier-hard and the blueprint says why.
- `sonnet` is the default worker tier; `haiku` is preferred for mechanical, high-volume roles (scanners, classifiers, formatters, log readers).
- `opus` for a worker is reserved for roles doing complex agentic implementation, and each such assignment carries benchmark `tier_evidence` in the blueprint.
- `fable` is capped at `default_model` plus at most ONE architect-class agent whose reasoning failure would poison everything downstream — never a whole tier of workers (`model: inherit` agents count as whatever `default_model` is).
- `effort` is omitted by default in frontmatter: workers then run at their model's default (`high` on `sonnet`/`haiku`/`fable`, `medium` on Opus 5.5 — Anthropic's deliberate default for `opus`, which resolves tasks with fewer steps and tokens). When the domain's judgment load genuinely needs the `opus` orchestrator at `high`, the blueprint sets `default_effort: high` (written to `settings.json` `effortLevel`) with a one-line reason; `xhigh` anywhere requires a stated justification; `max` is FORBIDDEN in generated frontmatter, `settings.json` and blueprints (official guidance: diminishing returns, prone to overthinking; settings keys do not even accept it).
- `qa-validator` reports a roster that breaks this budget as `tier_budget` CRITICAL and routes it back to `domain-architect`.
