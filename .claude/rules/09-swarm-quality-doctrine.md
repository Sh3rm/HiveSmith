# Global Rule: Swarm Quality Doctrine (Measured Anti-Patterns)

These directives encode Anthropic's officially published, measured findings about multi-agent systems, plus research results cited by journal or arXiv id (preprints marked as such). They bind `domain-architect` (design time), `persona-engineer` (write time), and `prompt-evaluator`/`qa-validator` (evaluation time) for every generated swarm.

**Directives:**

1. **Single-Agent Justification (burden of proof on decomposition):** "Multi-agent implementations typically use 3-10x more tokens than single-agent approaches for equivalent tasks" (claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them); against a chat baseline, agents use ~4x and multi-agent systems ~15x the tokens (anthropic.com/engineering/multi-agent-research-system). Parallelism buys thoroughness, not speed (same Anthropic blog), and planning is the work most harmed by decomposition — on the PlanCraft sequential-planning benchmark every multi-agent variant tested degraded 39–70% against a single-agent baseline (Kim et al., Nature Machine Intelligence 8:1157–1172, 2026; preprint arXiv:2512.08296). Also, "a well-designed single agent with appropriate tools can accomplish far more than many developers expect" (Anthropic). The same study (260 configurations, models up to Claude Sonnet 4.5) found that single-agent "baselines above approximately 45% predict zero-to-negative multi-agent gains", a threshold its authors read as "a practical selection rule rather than a universal scaling principle", and every multi-agent variant lost 1–13% on SWE-bench Verified. Measured on current agents, native dynamic concurrency (Claude Code's ultracode dynamic workflows on Opus 5, Codex, Kimi Code) helped most on long-horizon tasks but gave no gain on bounded SWE-bench Verified tasks (task pass unchanged for Codex, −24.0 points for Claude Code, −18.0 for Kimi Code), with end-to-end effects from −11.9 to +2.3 points and token use reaching "1.41–3.31 times that of sequential execution" (arXiv:2610.10263, preprint), so a bounded task (one issue, one fix) is not fanned out. Under equal thinking-token budgets single agents "consistently match or outperform" multi-agent systems on multi-hop reasoning (arXiv:2604.02460, preprint). In Anthropic's own role-split experiment, "the subagents spent more tokens on coordination than on actual work". There is therefore no target roster size: each agent is justified individually, and a single agent with rules and hooks is a valid design. Every blueprint MUST state in `single_agent_justification` why one well-tooled agent cannot do the job — the only valid grounds are context pollution, genuinely parallel independent workstreams, or a specialization threshold. Evaluators reject blueprints without it.

2. **Context-Boundary Decomposition, Not Phase Decomposition:** Splitting one body of work into sequential pipeline stages ("planner → implementer → tester → reviewer") is an official Anthropic anti-pattern — each handoff loses context ("telephone game"). Group tasks that share necessary context into ONE agent: the agent implementing a feature also writes its tests. GOOD boundaries: independent research paths, components with defined APIs, blackbox verification of finished output. BAD boundaries: sequential phases of the same work, tightly coupled components, anything needing constant state sync. `prompt-evaluator` flags phase-chain rosters as a category error routed back to `domain-architect`.

3. **Prompt Length Budget (documented):** Anthropic's guidance is to "target under 200 lines per CLAUDE.md file. Longer files consume more context and reduce adherence" (code.claude.com/docs/en/memory), and "Bloated CLAUDE.md files cause Claude to ignore your actual instructions!" (code.claude.com/docs/en/best-practices). No measurement is published for the figure; IFScale (arXiv:2507.11538, preprint) shows adherence decaying as instruction density grows, with "bias towards earlier instructions" — "even the best frontier models only achieve 68% accuracy" at 500 simple instructions. Generated orchestrator prompts must be complete but bounded: no filler, and content that isn't orchestration-critical modularized into `.claude/rules/` (path-scoped via `paths:` where applicable). `qa-validator` flags any generated `CLAUDE.md` exceeding ~200 lines. Since Claude Code 2.1.281 a startup warning also fires when files that are each within that length add up past a combined limit, and `@`-imports do not reduce context cost, so keep the always-loaded set lean as a whole. Depth of thought, not length of file, is the quality bar — the same discipline applies to agent bodies: rich in operational detail, zero boilerplate padding.

4. **Verifier Hardening ("early victory" countermeasure):** Verification agents are documented to produce false positives — declaring work done without thorough testing. Every generated verifier/reviewer/QA persona MUST carry explicit completeness language: "you MUST run the complete test suite", "you MUST test edge cases" — never a vague "verify this works". Completeness language alone is not enough: "many existing verifiers perform only superficial checks, despite being prompted to perform thorough verification" (MAST, arXiv:2503.13657), ten reviewers unanimously endorsed a non-existent vulnerability that "was killed only by a single empirical test" (arXiv:2604.19049, preprint), and LLM judges detect false "done" claims at AUROC ≤ 0.65 on tau2-bench and 0.54 on AppWorld (arXiv:2606.09863, preprint). Therefore: every verifier verdict MUST rest on at least one empirical check the verifier itself ran (a test, a command, opening the cited source) and name it; verifiers receive the artifact or the claims plus the acceptance criteria, NOT the author's reasoning — checking claims independently of the draft beats checking while reading it (Chain-of-Verification, arXiv:2309.11495); and a worker's "done" is a claim the orchestrator spot-checks, never a verdict. A passing test suite is evidence, not acceptance: METR found that "roughly half of test-passing SWE-bench Verified PRs written by mid-2024 to mid/late-2025 agents would not be merged into main by repo maintainers" (metr.org notes, 2026-03-10), so verifiers also check the stated requirements, not only that tests pass. A generator agent NEVER approves its own output; verification always runs in a fresh-context agent. Every generator-verifier loop has a maximum iteration count and a named fallback (escalate to the operator, or return the best attempt with its open defects listed): Anthropic notes that "a maximum iteration limit with a fallback strategy ... prevents this from becoming an infinite loop" (claude.com/blog/multi-agent-coordination-patterns). Fresh-context reviewers flag only correctness and requirement gaps, NOT style preferences — an evaluator told to find gaps will always find something, and nit-chasing causes over-engineering.

5. **Manifesto Verbatim, Artifacts Just-in-Time:** The user's original request and vision pass down VERBATIM (Visionary Context Passing — never compressed). Research artifacts, file contents, and large reference material are the opposite: pass lightweight identifiers (paths, queries, report filenames) and let each agent load what it needs at runtime via its tools — do not pre-dump bulk content into every delegation prompt.

6. **Tool Design Standards (for `tool-smith` and `mcp-integrator`):** Consolidate related operations into fewer, higher-level tools rather than many narrow API-mirroring ones — if a human engineer can't tell which of two tools to use, neither can an agent. Use consistent prefix namespacing for related tools. Custom tools return semantically meaningful identifiers (not opaque UUIDs), support concise/detailed response formats where output can be large, and emit actionable error messages that let the calling agent self-correct.

7. **Per-Task Fan-Out and Delegation Phrasing:** A generated orchestrator scales each fan-out to the task, per Anthropic's lead-agent guidance (anthropic.com/engineering/multi-agent-research-system; anthropics cookbook `research_lead_agent`): simple fact-finding → 1 agent (or none: never delegate what the orchestrator can finish in a few tool calls); direct comparisons → 2–4; complex research → 5–10+, at most 20. "Prefer fewer, more capable subagents over many overly narrow ones." Phrase delegation in the generated `CLAUDE.md` as an explicit standing request that names the occasions for fanning out (e.g. "For every comparison of two or more vendors, launch one researcher per vendor in a single message"), not as an abstract policy ("use subagents where appropriate"). Reason (an observation from a static read of the 2.1.284 binary, not documented behaviour): a server-gated section of Claude Code's system prompt for some Opus models includes "Do not use the Agent tool, workflows, or deep-research unless the user, a CLAUDE.md file, or a skill asks for it" (context: anthropics/claude-code#80988) — so a `CLAUDE.md` that actually asks is what keeps the swarm delegating.

8. **Model-Generation Prompting:** Generated personas follow the current model's prompting guide, not habits written for older models. Each text below is taken verbatim and in full from the prompting guide (platform.claude.com) of the model the worker's tier resolves to, because the guides differ; where that guide has no such text (the Opus 5.5 guide has neither the research nor the verification text), use the Sonnet 5.5 text:
   - Every generated research worker carries its model's research text. Sonnet 5.5: "Use the search tool to check specifics that may have changed since your training, such as what is allowed, required or charged, even when you feel confident. For researched work such as a report or a comparison, gather current sources rather than writing from your training knowledge." Haiku 5.5: its "Your training data ends well before today's date. ..." paragraph (the guide's companion current-date line is a template the caller fills, so it is left out of a static agent file).
   - Every generated worker that changes runnable code carries its model's verification paragraph ("When you change code that can be run, built, or type-checked, run a real check that exercises the change before reporting it done: ..."); the Haiku 5.5 guide notes that at `low` and `medium` the model "sometimes reports a code change as done without running a check."
   - Every generated autonomous (headless) worker carries its model's carry-through paragraph (Sonnet 5.5 begins "Keep working until everything the user asked for is done, and only stop to ask when you can't go on without the user or before a risky step."), alongside, never instead of, the swarm's risky-action rules (Rule 02; the guide notes it does not replace them). It is left out of agents that work with a human in the loop: the Opus 5.5 guide says to "leave the addition out of human-in-the-loop applications, where someone is there to answer." The generated README suggests `/doctor prompt-audit` (≥ 2.1.283) as an operator step: it audits `CLAUDE.md`, skills, agents and commands for patterns written for older models.

9. **Instruction Files Written for Current Models:** Recent Claude models follow instructions precisely — Anthropic documents that Opus 4.8 and Sonnet 5 interpret "prompts literally and explicitly, particularly at lower effort levels" (the 5.5 prompting guides do not repeat the statement) — so every line of a generated instruction file is likely to be acted on, and acting on it costs steps. Repository context files did "not generally improve task success rates, while increasing inference cost by over 20% on average", largely because agents followed them; this held "for both LLM-generated and developer-committed context files", though developer-written files outperformed generated ones (arXiv:2602.11988, preprint). Every generated `CLAUDE.md`, rule and agent body therefore follows these directives:
   - Keep only what the agent cannot discover or infer: "For each line, ask: 'Would removing this cause Claude to make mistakes?' If not, cut it" (code.claude.com/docs/en/best-practices). No repository overviews, directory listings or standard language conventions.
   - State the scope explicitly when an instruction should apply beyond the case it names, and give the reason behind any rule that is not self-evident (Anthropic: explaining "why such behavior is important" helps Claude "deliver more targeted responses").
   - Emphasis such as "IMPORTANT" goes on the one line agents keep skipping, not on many: "If you emphasize many lines, none of them stands out" (code.claude.com/docs/en/best-practices). Dial back stacked CRITICAL/MUST language: Anthropic observed that prompts written that way make Opus 4.5 and 4.6 "overtrigger" and advises "more normal prompting" (platform.claude.com prompting best practices). Quoted completeness language for verifiers (§4) is the deliberate exception.
   - No role inflation ("you are the world's best X"), emotional pressure, tips or threats: "Expert personas showed no consistent benefit across models" (arXiv:2512.05858) and "Threatening or tipping a model generally has no significant effect" (arXiv:2508.00614; both preprints). A one-sentence role that states the job is enough.
   - Prefer a goal, its boundaries and a runnable done-check over a scripted step list, and use numbered steps only where order or completeness matters. (For reasoning itself, Anthropic likewise finds that "a prompt like 'think thoroughly' often produces better reasoning than a hand-written step-by-step plan".)
   - No contradictions within or across files: "if two instructions contradict each other, Claude may pick one arbitrarily" (code.claude.com/docs/en/memory).
   `prompt-evaluator` reports violations as `outdated_prompting` findings routed to `persona-engineer`.
