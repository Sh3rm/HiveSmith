# Global Rule: Swarm Quality Doctrine (Measured Anti-Patterns)

These directives encode Anthropic's officially published, measured findings about multi-agent systems, plus research results cited by arXiv id (preprints marked as such). They bind `domain-architect` (design time), `persona-engineer` (write time), and `prompt-evaluator`/`qa-validator` (evaluation time) for every generated swarm.

**Directives:**

1. **Single-Agent Justification (burden of proof on decomposition):** "Multi-agent implementations typically use 3-10x more tokens than single-agent approaches for equivalent tasks" (claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them); against a chat baseline, agents use ~4x and multi-agent systems ~15x the tokens (anthropic.com/engineering/multi-agent-research-system). Parallelism buys thoroughness, not speed (same Anthropic blog), and planning is the work most harmed by decomposition — on the PlanCraft sequential-planning benchmark every multi-agent variant tested degraded 39–70% against a single-agent baseline (arXiv:2512.08296, preprint). Also, "a well-designed single agent with appropriate tools can accomplish far more than many developers expect" (Anthropic). Every blueprint MUST state in `single_agent_justification` why one well-tooled agent cannot do the job — the only valid grounds are context pollution, genuinely parallel independent workstreams, or a specialization threshold. Evaluators reject blueprints without it.

2. **Context-Boundary Decomposition, Not Phase Decomposition:** Splitting one body of work into sequential pipeline stages ("planner → implementer → tester → reviewer") is an official Anthropic anti-pattern — each handoff loses context ("telephone game"). Group tasks that share necessary context into ONE agent: the agent implementing a feature also writes its tests. GOOD boundaries: independent research paths, components with defined APIs, blackbox verification of finished output. BAD boundaries: sequential phases of the same work, tightly coupled components, anything needing constant state sync. `prompt-evaluator` flags phase-chain rosters as a category error routed back to `domain-architect`.

3. **Prompt Length Budget (measured):** A `CLAUDE.md` beyond ~200 lines measurably REDUCES instruction adherence — important rules get lost in noise. Generated orchestrator prompts must be dense but bounded: every section complete, no filler, and content that isn't orchestration-critical modularized into `.claude/rules/` (path-scoped via `paths:` where applicable). `qa-validator` flags any generated `CLAUDE.md` exceeding ~200 lines. Since Claude Code 2.1.281 the
large-instructions startup notice counts `CLAUDE.md`, rules and `@`-imports together, so the budget applies to
the always-loaded set as a whole, not to one file. Depth of thought, not length of file, is the quality bar — the same discipline applies to agent bodies: rich in operational detail, zero boilerplate padding.

4. **Verifier Hardening ("early victory" countermeasure):** Verification agents are documented to produce false positives — declaring work done without thorough testing. Every generated verifier/reviewer/QA persona MUST carry explicit completeness language: "you MUST run the complete test suite", "you MUST test edge cases" — never a vague "verify this works". Completeness language alone is not enough: "many existing verifiers perform only superficial checks, despite being prompted to perform thorough verification" (MAST, arXiv:2503.13657), ten reviewers unanimously endorsed a non-existent vulnerability that "was killed only by a single empirical test" (arXiv:2604.19049, preprint), and LLM judges detect false "done" claims at AUROC ≤ 0.65 on tau2-bench and 0.54 on AppWorld (arXiv:2606.09863, preprint). Therefore: every verifier verdict MUST rest on at least one empirical check the verifier itself ran (a test, a command, opening the cited source) and name it; verifiers receive the artifact or the claims plus the acceptance criteria, NOT the author's reasoning — checking claims independently of the draft beats checking while reading it (Chain-of-Verification, arXiv:2309.11495); and a worker's "done" is a claim the orchestrator spot-checks, never a verdict. A generator agent NEVER approves its own output; verification always runs in a fresh-context agent. Fresh-context reviewers flag only correctness and requirement gaps, NOT style preferences — an evaluator told to find gaps will always find something, and nit-chasing causes over-engineering.

5. **Manifesto Verbatim, Artifacts Just-in-Time:** The user's original request and vision pass down VERBATIM (Visionary Context Passing — never compressed). Research artifacts, file contents, and large reference material are the opposite: pass lightweight identifiers (paths, queries, report filenames) and let each agent load what it needs at runtime via its tools — do not pre-dump bulk content into every delegation prompt.

6. **Tool Design Standards (for `tool-smith` and `mcp-integrator`):** Consolidate related operations into fewer, higher-level tools rather than many narrow API-mirroring ones — if a human engineer can't tell which of two tools to use, neither can an agent. Use consistent prefix namespacing for related tools. Custom tools return semantically meaningful identifiers (not opaque UUIDs), support concise/detailed response formats where output can be large, and emit actionable error messages that let the calling agent self-correct.

7. **Per-Task Fan-Out and Delegation Phrasing:** A generated orchestrator scales each fan-out to the task, per Anthropic's lead-agent guidance (anthropic.com/engineering/multi-agent-research-system; anthropics cookbook `research_lead_agent`): simple fact-finding → 1 agent (or none: never delegate what the orchestrator can finish in a few tool calls); direct comparisons → 2–4; complex research → 5–10+, at most 20. "Prefer fewer, more capable subagents over many overly narrow ones." Phrase delegation in the generated `CLAUDE.md` as an explicit standing request that names the occasions for fanning out (e.g. "For every comparison of two or more vendors, launch one researcher per vendor in a single message"), not as an abstract policy ("use subagents where appropriate"). Reason (an observation from a static read of the 2.1.284 binary, not documented behaviour): a server-gated section of Claude Code's system prompt for some Opus models includes "Do not use the Agent tool, workflows, or deep-research unless the user, a CLAUDE.md file, or a skill asks for it" (context: anthropics/claude-code#80988) — so a `CLAUDE.md` that actually asks is what keeps the swarm delegating.

8. **Model-Generation Prompting:** Generated personas follow the current model's prompting guide, not habits written for older models. Every generated research worker carries the Sonnet 5.5 guide's research text verbatim: "Use the search tool to check specifics that may have changed since your training, such as what is allowed, required or charged, even when you feel confident. For researched work such as a report or a comparison, gather current sources rather than writing from your training knowledge." Every generated autonomous (headless) worker carries the guide's carry-through text — "Keep working until everything the user asked for is done, and only stop to ask when you can't go on without the user or before a risky step." — alongside, never instead of, the swarm's risky-action rules (Rule 02; the guide notes it does not replace them). The generated README suggests `/doctor prompt-audit` (≥ 2.1.283) as an operator step: it audits `CLAUDE.md`, skills, agents and commands for patterns written for older models.
